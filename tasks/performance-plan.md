# 性能与架构优化路线计划

本文件只管理性能/架构优化的执行顺序与完成状态，独立于 [SPEC](../SPEC.md) 的应用框架任务（[plan](plan.md)、[todo](todo.md)）。`[x]` 表示本行验收与定向验证已满足，不表示浏览器或真机表现已确认；`[-]` 表示测量后按门槛关闭；`[ ]` 为待实施或暂缓。

## 原则

- 先测量，后优化：P0 的基线是 P1 之后所有任务的前置条件。热点在压力场景中占单帧预算约 10% 以上，或引起可见 GC 抖动时才实施；未达到的任务记录测量后关闭，不为“看起来慢”改代码。
- 保持契约：不改已有函数名、包名和 0.4.0 已发布行为（例如 `new Engine()` 不传 `diagnostics` 时仍采集 timings）。需要改变规格语义的任务先更新对应 `docs/specs/*`，再改实现。
- 不重写内核：不引入 Archetype、WebGL 后端或 3D；Canvas 2D 继续使用。P4 的结构调整仅在基准证明必要时进行，且保持公开 API。
- 每个任务在同一台机器上记录优化前后的中位数/最小/最大值，原始 JSON 存入 `docs/performance/`。Node 模拟 Canvas 的结果不能写成浏览器帧率提升。

## 依赖与顺序

```text
P0 基线 ──► P1 低风险去分配（各任务互相独立，可并行）
       └──► P2 中等改动（O7/O8 共用模板协调逻辑，串行；O9 只涉及碰撞，可独立进行）
P3 结构整理（R1/R3 不依赖测量，可随时进行；R2 需先更新规格）
P4 按需（仅由 P0/P1 复测数据触发）
```

## P4：按需（仅由测量触发）

| 状态 / ID | 触发条件                             | 内容                                                                                                                    |
| --------- | ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| [ ] E1    | 压力场景中查询或组件读写成为主要耗时 | 稀疏集的索引从 `Map` 改为数组/`Int32Array`；新增不分配的 `world.each(tokens, fn)` 入口，`query` 语义（handle 快照）不变 |

明确不做：Archetype/列式存储重写、WebGL 后端、通用对象池框架。以后有真实需求和测量数据时再立项。

## 验证节奏

- 每个任务只运行自己的定向测试；改了类型或公开入口时运行 `npm run typecheck`。
- 性能任务完成后用 B1 的同一组场景复测，前后数据写入 `docs/performance/` 并更新 README 表格；没有显著差异时如实记录，按原则决定是否保留改动。
- 浏览器复测（B2 场景）只在 P1/P2 结束后、获得授权时执行一次，不作为每个任务的固定步骤。

## 风险

| 风险                         | 处理                                                                                          |
| ---------------------------- | --------------------------------------------------------------------------------------------- |
| 结构共享让外部对象泄漏进快照 | 只复用 snapshot 自己产出、记录在 WeakSet 中的冻结对象，用户传入的冻结对象仍然复制             |
| computed 截断导致漏更新      | 只对原始值做 `Object.is` 判断；对象结果仍按变化处理；动态依赖切换必须有回归测试               |
| 绘制去分配改变绘制顺序或状态 | 保持稳定排序和 save/restore 语义，renderer 测试比对绘制调用序列                               |
| 统一循环改变旧入口时序       | 先补齐 `runBrowser` 现有行为测试，再迁移                                                      |
| 网格宽阶段改变回调顺序或漏检 | 输出按现有扫描顺序排序；用暴力结果做多种子比对；文档中 O(n²) 退化说明同步更新为网格的退化条件 |
| 优化收益在噪声范围内         | 按中位数和最小/最大值区间判断，噪声内的改动不宣称提速                                         |

R1 结果（2026-11-07）：browser 包新增 `createFrameLoop`，`runBrowser` 与 `GameCanvas` 共用。时间间隔上限保持两者原有策略：`runBrowser` 不限制（固定步由 Engine `maxSteps` 限制），`GameCanvas` 限制为 1 秒。先补的行为测试在旧实现上通过，迁移后不变。顺带修正两个旧问题，均有改动前失败的测试：

- `GameCanvas` 使用默认浏览器驱动时，`dispose()` 没有取消已请求的帧（原来只取消 `options.driver`）。
- 系统在帧内调用 `engine.pause()` 后，`runBrowser` 没有重置帧计时，恢复后第一帧会收到整个暂停时长。
