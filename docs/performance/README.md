# 性能测量

命令：`npx tsx --conditions=source scripts/benchmark.ts <输出.json>`。Node 26.7 / Linux，同机各批次先预热 5 次，再测 15 次，单位为每批毫秒。基线为 0.3.0，初步结果为热路径优化后、2D 扩展前。原始数据见 [基线](before.json) 和 [初步结果](after-core.json)。

| 样本                           | 基线中位数 → 初步结果 | 说明                                                               |
| ------------------------------ | --------------------- | ------------------------------------------------------------------ |
| 10,000 实体，1 组件，20 次查询 | 18.49 → 11.79 ms      | 复用生命周期内冻结 handle，保留快照、World 与代际检查              |
| 10,000 实体，4 组件，20 次查询 | 23.75 → 16.53 ms      | 同上，查询交集行为未改变                                           |
| 1,000 图形，20 次遍历/排序     | 16.75 → 3.23 ms       | 绘制项只获取一次组件；使用模拟 Canvas，不能称为浏览器帧率提升      |
| 1,000 系统，100 步，默认诊断   | 9.88 → 9.16 ms        | 差异仍处于样本波动范围，不宣称默认系统执行获得显著提升             |
| 1,000 系统，100 步，关闭诊断   | 9.02 → 1.08 ms        | 0.3.0 不支持关闭；这是新增可选配置的开销差异，不是相同设置的加速比 |

数组快照优化采用写时替换，保留执行中新增系统到下一阶段生效、删除系统不改变当前阶段快照的契约。before/after 调度计划在结构变更时重建。查询缓冲没有跨迭代器共享，避免嵌套/交错遍历互相覆盖。

已补充独立实验及 2D 扩展后复测，见 [隔离实验](isolated.json)、[最终 Node 样本](final.json) 和 [真实 Chromium 样本](browser.json)。

隔离命令：`npm run benchmark:isolated -- <输出.json>`，从 Git v0.3.0 读取原实现并在临时模块中单独替换 handle 或 require。21 次样本中，handle 单独优化查询中位数 20.30 → 13.28 ms（有 GC/调度离群值，按中位数和重复测量判断）；require 单独优化旧绘制路径 21.33 → 14.42 ms（优化最大 15.49 小于原最小 18.50）。两者均保留。

真实浏览器命令：`npm run test:2d -- <输出.json>`。同一 Chromium、同一 Canvas 尺寸、1,000 图形 ×20 次绘制，每批读回像素，预热 5 批、采样 15 批。原 0.3.0 中位数 26.70 ms（22.90–33.80），包括 2D 新能力的当前实现 11.80 ms（10.40–13.10）。这是本机压力批次结果，不能换算为所有设备的帧率提升。

当前默认诊断系统开销 9.81 ms，与原 9.88 处于噪声内，不宣称默认调度提速；关闭诊断可降至 1.27 ms，但这是显式配置选择。最终纯 JS 绘制批次为 4.50 ms，较早期 3.23 ms 增加了新能力分支，仍优于原 16.75 ms。没有改变稀疏集布局，也没有加入永久层级排序缓存，因为 layer 可以直接修改。未实施 Archetype、TypedArray 存储或跨帧绘制排序缓存。

系统约束缓存独立样本：100 个固定系统形成依赖链，100 步/批。A 阶段逐阶段重编译的中位数 4.84 ms（4.40–5.74），缓存后 0.117 ms（0.115–0.284）；同为 diagnostics:false，保留此优化。

### O4 碰撞去分配

改动：矩形包围盒和中心点直接用矩阵分量计算，不再创建临时点数组或用 `Math.min(...)` 展开；碰撞模块的碰撞对 key 从拼接字符串改为打包的整数索引，回收复用的索引通过实体 handle 身份区分。新增两个定向测试（旋转/偏移/缩放的包围盒、同一步内回收索引的 enter/exit），改动前后的实现都能通过。

同机复测两轮（每批 20 帧，中位数，ms）：

| 样本               | 基线两轮      | O4 后两轮     | 单帧              |
| ------------------ | ------------- | ------------- | ----------------- |
| 宽阶段检测 500 体  | 11.33 / 11.47 | 8.19 / 8.06   | 约 0.57 → 0.41 ms |
| 碰撞模块 500 体    | 12.90 / 11.66 | 8.85 / 8.47   | 约 0.61 → 0.43 ms |
| 宽阶段检测 2000 体 | 59.54 / 58.57 | 40.48 / 44.18 | 约 3.0 → 2.1 ms   |
| 碰撞模块 2000 体   | 63.56 / 56.84 | 41.59 / 42.85 | 约 3.0 → 2.1 ms   |

碰撞对数量不变（180 / 638）；同批的精灵绘制样本（8.38 / 9.09 → 9.28 / 9.16）作为未改动的参照，没有同向变化。2000 体仍高于约 1.7 ms 的门槛。对 2000 体做的一次拆分测量中，查询加组件读取约占 15%，变换解析约 20%，其余约 65% 是单轴扫描、排序和精确相交检查，继续下降需要改宽阶段算法，不在本任务范围内。

### O9 网格宽阶段（可选）

不同时间的整批基准波动可达 ±30%，因此用同一进程内交替执行的 A/B（每批 20 帧，取中位数，单位 ms）比较 O4 版扫描、改动后的默认路径和 `cellSize: 40` 的网格：

| 场景                   | O4 扫描 | 当前默认 | 网格 cellSize 40 |
| ---------------------- | ------- | -------- | ---------------- |
| 均匀 50 体             | 0.51    | 0.48     | 0.62             |
| 均匀 500 体            | 4.42    | 4.55     | 5.43             |
| 均匀 2000 体           | 24.30   | 24.06    | 29.18            |
| 密集 500 体（6588 对） | 16.16   | 15.14    | 29.01            |
| 含大碰撞体 500 体      | 10.41   | 9.94     | 15.98            |
| 窄竖条 1000 体         | 82.63   | 68.11    | 21.65            |

网格每帧要建立格子映射，在常见分布下比 X 轴扫描慢 20–90%，只在碰撞体挤在窄竖条、X 轴扫描退化时快约 3.8 倍，因此不作默认，只作 `cellSize` 可选项。默认路径与 O4 相同，差异在噪声内。早期曾测试按当帧尺寸自动推算格子、64 体以上自动启用网格，以及“按分布较宽的轴扫描”的原型；后者常规场景与扫描持平、窄竖条约 25 ms，未采用。

同进程测量下，均匀 2000 体的 X 轴扫描约 1.2 ms/帧，已低于约 1.7 ms 的门槛；完整基准中约 1.9–2.0 ms/帧，差异来自前序场景留下的内存回收压力。另在密集 500 体（6588 对）中，碰撞模块每批 50.11 ms，只做检测为 15.95 ms，大量碰撞对时 enter/stay/exit 记录成为主要开销，尚未处理。
